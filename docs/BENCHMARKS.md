# Benchmarks

Generated by `go run ./tools/bench` on 2026-10-25: AMD Ryzen 5 PRO 4650U with Radeon Graphics, 12 logical CPUs, linux/amd64, Go 1.27.3. Postgres 16 in a
local Docker container (testcontainers), one orchestrator replica in process, workers as
goroutines speaking the real HTTP worker protocol. Everything shares one machine, so the
numbers are relative, not capacity planning; no race detector.

## Claim throughput and latency

Each run preloads 2000 ready single-step tasks, then N workers loop: claim one task
(long-poll 100ms), complete it, repeat until all are done. Claim latency is the client-side
time of a claim request that returned a task (transaction, lease, HTTP); empty polls at the
end of a run are excluded. Throughput is completed tasks per second of the whole run.

| Workers | Throughput (tasks/s) | Claim p50 | Claim p99 |
|---|---|---|---|
| 1 | 74 | 9.94ms | 19.96ms |
| 2 | 159 | 9.08ms | 17.69ms |
| 4 | 254 | 10.77ms | 19.24ms |
| 8 | 361 | 14.98ms | 25.86ms |
| 16 | 420 | 23.35ms | 41.28ms |
| 32 | 445 | 38.27ms | 88.5ms |
| 64 | 448 | 63.3ms | 133.91ms |

## Decision latency

Triage of one timeout error. RulePolicy is called in a tight loop; LayaPolicy (fp32, CPU)
is called by 1, 4 and 8 concurrent callers, 8 calls each, with the default session
layout: two runs in flight, half the CPU threads each, no batching.

| Policy | Concurrent callers | p50 | p99 | Decisions/s |
|---|---|---|---|---|
| RulePolicy | 1 | 55µs | 168µs | 15308.2 |
| LayaPolicy (fp32) | 1 | 751.9ms | 760.205ms | 1.4 |
| LayaPolicy (fp32) | 4 | 2.089349s | 2.226328s | 1.9 |
| LayaPolicy (fp32) | 8 | 4.166797s | 4.508677s | 1.9 |

### Session layout

Throughput with 8 concurrent callers (32 decisions) for different ONNX Runtime layouts;
this is why batching is off by default.

| Runs in flight | Threads per run | Max batch | Decisions/s |
|---|---|---|---|
| 2 | 6 | 8 | 1.42 |
| 1 | 12 | 8 | 1.44 |
| 1 | 12 | 1 | 1.63 |

Notes:

- Claim throughput levels off around 16 workers: every write goes through the one leader
  (ADR 0003) and each claim is a transaction of about ten statements plus six per task,
  all on the database clock and fenced. More workers then mostly add queueing (p99).
- The same statement count makes the system latency-sensitive: in the chaos suite, with
  60±30ms added to every database round trip, a claim takes about two seconds.
- Laya inference is CPU-bound at roughly 0.5s of CPU per decision on this machine, so
  extra concurrency raises latency, not throughput. Padded batching did not help on CPU,
  which is why it is off by default (the table above).
- A closed ONNX Runtime session's memory is not returned to the OS: loading the 1.7GB model
  repeatedly in one process grows RSS by roughly that much per load. Baton loads it once
  per process; the layout sweep runs each layout in a child process for this reason.
